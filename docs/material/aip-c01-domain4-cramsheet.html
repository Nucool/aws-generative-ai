4.1 Cost optimization and resource efficiency

4.1.1 Token efficiency systems

token estimation/trackingcontext window optimizationprompt compressioncontext pruningresponse limiting
Key: Cut cost via token tracking, context-window optimization, prompt compression, context pruning and response-size limits (max tokens).
Trap: "remove all length limitations" when the requirement specifies a length (e.g. 50-100 words) = wrong; you must set max tokens, not drop it.

4.1.2 Cost-effective model selection

cost-capability tradeofftiered FM usage by complexityprice-to-performance
Key: Tier models by query complexity (small for routine, large for complex); balance inference cost vs quality. Cheapest customization that solves it: prompt eng < RAG < fine-tune < continued pre-training < from scratch.
Trap: "select the cheapest option regardless of baseline latency" = wrong when latency is a requirement. Train-from-scratch is almost always the over-engineered distractor.

4.1.3 High-performance / max resource utilization

batching strategiescapacity planningauto-scalingProvisioned Throughput optimization
Key: Maximize throughput with batching, capacity planning, utilization monitoring, auto-scaling and provisioned-throughput tuning.
Watch: Provisioned Throughput over-sized "to absorb the highest expected spike" is expensive — a red flag when cost-effectiveness is required and traffic is spiky.

4.1.4 Intelligent caching systems

semantic cachingprompt cachingresult fingerprintingdeterministic request hashingedge caching
Key: Repeated / near-identical queries (e.g. "35% share identical context") → prompt caching / semantic caching to skip re-processing. Pair with latency-optimized inference for low latency + cost.
Trap: Repeated-query problems are solved by caching, not by Intelligent Prompt Router (that's for complexity routing) and not by a separate ElastiCache tier when native prompt caching exists.

4.2 Optimize application performance

4.2.1 Responsive systems (latency-cost tradeoff)

pre-computationlatency-optimized Bedrock modelsparallel requestsresponse streaming
Key: Low latency → latency-optimized inference + response streaming; pre-compute predictable queries; parallelize complex workflows.

4.2.2 Retrieval performance

index optimizationquery preprocessinghybrid search + custom scoring
Key: Improve retrieval relevance/speed with index optimization, query preprocessing and hybrid search with custom scoring.

4.2.3 Throughput optimization

token processing optimizationbatch inferenceconcurrent invocation management
Key: Raise throughput via token-processing optimization, batch inference and managed concurrency.

4.2.4 FM performance (parameter tuning)

model-specific paramsA/B testingtemperature + top-k/top-p
Key: Temperature: low = consistent/factual, mid = balanced (creative + controlled), high = creative. Set max tokens for length. Balance requirement ("creative but controlled") → mid values, not extremes.
Trap: temperature 0.9 + large top-k when the ask is "controlled/consistent" = too random. temperature 0 when the ask is "variation/creative" = too rigid.

4.2.5 Efficient resource allocation

capacity planning (tokens)utilization monitoringauto-scaling for GenAI traffic
Key: Plan capacity for token throughput; monitor prompt/completion patterns; auto-scale to GenAI traffic shapes.

4.2.6 System performance for GenAI workflows

Key: Profile prompt-completion patterns, optimize vector-DB queries, apply LLM-specific latency reduction and efficient service comms.

4.3.2 Comprehensive GenAI monitoring / KPIs

Key: Track token usage, prompt effectiveness, hallucination rates, response quality; anomaly detection for token bursts/response drift; Model Invocation Logs for detailed request/response analysis.
Watch: Response times climbing under concurrent load → check CloudWatch throttling/latency metrics (quota). Inconsistent numeric answers → FM math limitation, fix with tool/function calling or lower temperature.
