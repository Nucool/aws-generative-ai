5.1 Evaluation systems for GenAI

5.1.1 Assessment frameworks (quality metrics)

relevancefactual accuracyconsistencyfluency
Key: Evaluate FM output on relevance, factual accuracy, consistency, fluency — beyond traditional ML metrics. BLEU=translation, ROUGE=summarization, BERTScore=semantic meaning, RAGAS=RAG pipeline.
Watch: BLEU/ROUGE = surface n-gram overlap (need a reference); BERTScore = meaning (handles paraphrase). No reference available → LLM-as-a-Judge or human eval.

5.1.2 Systematic model evaluation (find optimal config)

Bedrock Model EvaluationsA/B & canary testingmulti-model evalrobustness metrics
Key: Bedrock Model Evaluation for correctness/quality; robustness metrics for "sensitivity to slight input variations / consistency". A/B testing = compare multiple models to select the best.
Trap: "quantitative robustness / sensitivity to variations" → Model Evaluation robustness metrics, NOT Comprehend similarity, NOT temp-0 + Levenshtein (temp 0 kills variation; Levenshtein = surface only), NOT custom pipelines.

5.1.3 User-centered evaluation

feedback interfacesrating systemsannotation workflows
Key: Continuous improvement from user feedback, output rating systems and annotation workflows.

5.1.4 Systematic QA processes

continuous evaluationregression testingautomated quality gates
Key: Maintain standards with continuous evaluation, output regression testing and automated quality gates on deployment.

5.1.5 Multi-perspective assessment

RAG evaluationLLM-as-a-Judgehuman feedbackCreateEvaluationJob API
Key: LLM-as-a-Judge = managed evaluator, human-like judgment, scales to thousands, low overhead — for nuance (tone/context) that automated metrics miss. Native via CreateEvaluationJob API with a consistent evaluator model. Mix built-in metrics (correctness/relevance/formality) + custom metrics (company tone/style).
Trap: LLM-as-a-Judge done as separate batch jobs + custom judge + Lambda stats = high overhead; native CreateEvaluationJob wins. (Lambda + Spearman for the stats step is fine — the overhead is in generation/eval, not the stat.) Use a human-validated dataset for company-specific eval, not an industry benchmark.

5.2 Troubleshoot GenAI applications

5.2.1 Content handling issues (context window)

context-window overflow diagnosticsdynamic chunkingprompt designtruncation analysis
Key: Incomplete processing → diagnose context-window overflow, apply dynamic chunking, optimize prompt design, analyze truncation errors.

5.2.2 FM integration issues (API)

error loggingrequest validationresponse analysis
Key: Fix API integration problems with error logging, request validation and response analysis.

5.2.3 Prompt engineering problems

prompt testing frameworksversion comparisonsystematic refinement
Key: Improve response quality/consistency with prompt-testing frameworks, version comparison and systematic refinement.

5.2.4 Retrieval system issues

relevance analysisembedding quality diagnosticsdrift monitoringchunking/preprocessing remediationreranking
Key: Diagnose retrieval by layer — relevance analysis, embedding-quality diagnostics, drift monitoring, chunking/vectorization fixes, vector-search performance. Retrieval fine but ordering off → reranking.
Trap: Isolate the failing layer: bad retrieval → embeddings/chunking; right chunks wrong order → reranking; bad generation → prompt/grounding. Don't re-chunk when the stem says chunking is already correct.

5.2.5 Prompt maintenance issues

template testingCloudWatch Logs (prompt confusion)X-Ray (observability)schema validation
Key: Continuously improve prompts with template testing, CloudWatch Logs to diagnose prompt confusion, X-Ray observability, schema validation for format drift.

Domain 5 golden rule: pick the metric that matches the task (BLEU/ROUGE/BERTScore/RAGAS); LLM-as-a-Judge for nuance at scale via native CreateEvaluationJob; A/B to compare-and-select vs Canary/Blue-Green/Linear to safely roll out; and when troubleshooting retrieval, isolate the failing layer before choosing a fix.
