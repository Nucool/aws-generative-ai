1.1 Analyze requirements and design GenAI solutions

1.1.1 Architectural designs aligned to business needs & constraints

Bedrockintegration patternsdeployment strategies
Key: Pick FM + integration + deployment that match the stated constraints (latency, cost, residency, scale). Every requirement must map to a component.
Trap: An answer satisfying 2 of 3 requirements looks complete. Always read the last sentence before the question — the governing constraint (least overhead / real-time / no public internet) usually hides there.

1.1.2 Technical proof-of-concept before full deployment

Bedrock
Key: Validate feasibility, performance and business value on Bedrock first; full-scale build comes after the PoC proves value.
Trap: Choosing a full production build (train / fine-tune / self-host) when the scenario only asks to validate feasibility.

1.1.3 Standardized components for consistent implementation

Well-Architected FrameworkWA Tool — GenAI Lens
Key: "consistent across multiple deployment scenarios / business units" → standardized reusable components + WA GenAI Lens review.
Watch: WA Lens is a review/design tool — it never enforces anything at runtime (that is SCP / IAM / Guardrails).

1.2 Select and configure FMs

1.2.1 Assess and choose FMs (benchmarks, capability, limitations)

Bedrock Model Evaluationbenchmarks
Key: Match model size to task — small model = routine, low-latency, cheap; large model = reasoning, creative, in-depth explanation.
Trap: Limitation evaluation is the point. Intelligent Prompt Router routes only within one model family. Titan↔Claude, Llama↔Claude, Nova↔Claude are cross-family → the native router cannot do it; custom routing is required.

1.2.2 Dynamic model selection / provider switching without code changes

AWS AppConfigLambdaAPI Gateway
Key: AppConfig = dynamic config, instant propagation, no redeploy. One Lambda reads routing config and selects the FM at runtime.
Trap: "dedicated Lambda per FM" means adding a model touches code (violates "without code modification"). "Update via Console or CLI" = manual, fails hourly-updated metrics. Parameter Store = static config, weaker than AppConfig for frequent change. Lambda authorizer doing business routing = wrong job for the service.

1.2.3 Resilient AI systems during service disruption

Step Functions circuit breakerCross-Region Inferencefallback modelgraceful degradation
Key: "avoid single point of failure" → look for a fallback model. Cross-Region Inference exists for limited regional availability / resilience.
Trap: Cross-Region inference contradicts data residency. If inference must stay in the customer's Region, "cross-Region" or "consolidate into a single centralized deployment" is instantly wrong — deploy per-Region copies instead.

1.2.4 FM customization deployment & lifecycle management

SageMaker AIModel RegistryLoRA / adaptersCustom Model ImportProvisioned Throughput
Key: Import a fine-tuned HF / Safetensors model → Custom Model Import; guaranteed production throughput → Provisioned Throughput. Model Registry = versioning + rollback. LoRA = parameter-efficient adaptation.
Watch: "production" alone does not mean Provisioned. Provisioned when custom/fine-tuned model OR "specific / guaranteed / consistent throughput". On-Demand when base FM + variable, spiky traffic + cost focus.

1.3 Data validation and processing pipelines for FM consumption

1.3.1 Data validation workflows for quality standards

Glue Data QualitySageMaker Data WranglerLambdaCloudWatch metrics
Key: Validation = rules that check quality before FM consumption. Data Wrangler = low-code prep and transformation.
Trap: "validation rules that check consistency" ≠ "ensure consistent inputs". When the requirement says ensure/create consistency, the answer must actively transform (normalize / reformat), not merely validate.

1.3.2 Complex / multimodal processing (text, image, audio, tabular)

Bedrock Data AutomationBedrock multimodalTranscribeSageMaker ProcessingTextract
Key: Documents + audio + video in one managed service → BDA (least overhead). BDA structure: one project holding many blueprints; BDA auto-detects the blueprint from the document type.
Trap: BDA does not auto-select a project — "three separate projects and BDA picks one" is wrong. A BDA blueprint is an extraction template, not an orchestrator; it cannot drive Rekognition/Bedrock steps (Step Functions does that).

1.3.3 Format input data per model-specific requirements

JSON for Bedrock APISageMaker payloadsconversation formattingJSON Schema
Key: Evaluation / prompt datasets are JSONL in S3. Dialog apps need conversation-turn formatting. Deterministic structured output → JSON Schema.

1.3.4 Enhance input data quality for better FM responses

Bedrock reformat textComprehend entitiesLambda normalize
Key: Canonical chain → Comprehend extracts entities → normalize categories/specs → Bedrock reformats for optimal FM processing. Using an FM to reformat data is an exam-correct pattern.
Trap: Do not dismiss "use Bedrock to reformat" as over-engineering. And never strip or standardize away slang, tone or local expressions when tone/intent is the signal — that destroys the data (fine-tuning is the fix there).

1.4 Design and implement vector store solutions

1.4.1 Advanced vector database architectures

Bedrock Knowledge BasesOpenSearch + Neural pluginAurora pgvectorRDS + S3DynamoDBMemoryDB
Key: KB = hierarchical organization + managed store; OpenSearch Neural = topic segmentation; MemoryDB = in-memory, lowest latency.
Trap: Index algorithm follows dataset size + accuracy need: small dataset + "highly accurate" → Flat (exact), not HNSW. HNSW = large dataset + approximate/fast. Migrating the whole store to a graph DB is over-engineering.

1.4.2 Metadata frameworks for search precision

S3 object metadatacustom attributestaggingKendra metadata
Key: Metadata (timestamps, authorship, domain tags) drives filtering and context awareness. Enriching KB documents with metadata beats running separate search pipelines.
Watch: "seamlessly integrate" → enrich one centralized KB. Phrases like "separate pipelines / independently / stored outside the centralized knowledge base" mark the wrong answers.

1.4.3 High-performance vector architectures at scale

OpenSearch shardingmulti-indexhierarchical indexing
Key: Scale via sharding, per-domain multi-index, hierarchical indexing. Prefer horizontal scaling for growth.
Trap: Raising embedding dimensions (768 → 4096) "while keeping chunking unchanged" fixes nothing — it grows the index and worsens latency.

1.4.4 Integration components to connect resources

KB data source connectorsQ Business connectorsKendra
Key: Use built-in data source connectors for CMS, wikis and document systems instead of custom ingestion code.
Trap: "custom Lambda functions to process and index before importing" = avoidable overhead whenever a connector exists.

1.4.5 Data maintenance — keeping vector stores current

automatic synchronizationincremental updateEventBridge change detectionscheduled refresh
Key: Automatic sync on the data source = least overhead. Continuous change → event-driven / incremental updates, not manual reindexing.
Trap: "scheduled reindexing jobs + custom tagging rules each cycle" = high overhead; "periodically" also conflicts with a "continuous updates" requirement.

1.5 Design retrieval mechanisms for FM augmentation

1.5.1 Document segmentation / chunking

Bedrock KB chunkingfixed-sizesemantichierarchical
Key: Fixed-size = flat simple content. Semantic = split on natural meaning boundaries (fixes fractured context). Hierarchical = parent-child structure (article → paragraph); retrieve the child, pass the parent as context.
Trap: Do not swap the two. "fixed 500-token blocks fracture claims and rationale" → semantic. "must preserve relationships between articles and their paragraphs / headers" → hierarchical. Latency and index-growth figures in the stem are usually bait; the root cause is chunking.

1.5.2 Embedding solution selection

Titan EmbeddingsBedrock embedding modelsLambda batch embedding
Key: Choose on dimensionality + domain fit; automate embedding generation for new and updated content.
Watch: More dimensions is not better — it costs index size and latency. Re-embed whenever the chunking strategy changes.

1.5.3 Deploy and configure vector search

OpenSearch vector searchAurora pgvectorKB managed vector store
Key: Managed KB vector store = least overhead. OpenSearch / pgvector when you need control or already run that estate.

1.5.4 Advanced search architectures (relevance & accuracy)

hybrid searchBedrock reranker modelsKB reranking
Key: Hybrid search = dense semantic + keyword exact-term. Reranking = reorder retrieved chunks by relevance before generation, with no LLM retraining.
Trap: If the stem confirms embeddings, chunking and similarity scoring are already correct, the answer is reranking — not bigger chunks, not re-embedding. Higher throughput or speed never fixes contextual quality.

1.5.5 Query handling systems

Bedrock query expansionLambda query decompositionStep Functions query transformation
Key: Improve retrieval on the query side: expand vague queries, decompose multi-part questions, transform before search.

1.5.6 Consistent access mechanisms for FM integration

function callingMCP clientsstandardized API patternsRetrieveAndGenerate
Key: Retrieve returns chunks only. RetrieveAndGenerate retrieves, generates the answer, and returns citations automatically.
Trap: Requirement "must generate responses and cite the authoritative source" → RetrieveAndGenerate. Picking plain Retrieve leaves you building generation and citations yourself = extra overhead and a wrong answer.

1.6 Prompt engineering strategies and governance

1.6.1 Model instruction frameworks (control behavior & output)

Prompt Management — role definitionsGuardrails — responsible AItemplate configs
Key: Division of duties — Prompt Management holds roles, templates and response format; Guardrails enforces safety policy.
Trap: Guardrails never perform RBAC or model-access control. An option reading "Guardrails enforce safety policies and role-based access controls" is wrong — RBAC belongs to IAM / Prompt Management resource permissions.

1.6.2 Interactive systems: context and conversation state

DynamoDB historyStep Functions clarificationComprehend intent
Key: Conversation history → DynamoDB: low latency, concurrent sessions, TTL for auto-expiry, GSI for metadata search and filtering.
Watch: "automatically delete conversations when they expire" = DynamoDB TTL. RDS and S3 do not fit low latency plus native expiry.

1.6.3 Prompt management & governance (consistency + oversight)

Prompt Management — parameterized templates, versions, approvalS3 template repoCloudTrailCloudWatch LogsIAM
Key: Templates use {{variables}} filled at runtime. Prompts are account-level resources, so IAM controls who can create, edit and publish versions — that is the real RBAC. Versions are immutable snapshots → consistency + audit + approval workflow; CloudTrail records changes and usage.
Trap: Check where RBAC is attached. Right = Prompt Management / IAM. Wrong = Guardrails. Building your own Git + Lambda versioning is needless overhead.

1.6.4 Quality assurance for prompts

Lambda verify outputStep Functions edge casesCloudWatch regression
Key: Automated output verification + edge-case tests + a regression gate before promoting a prompt version to production.

1.6.5 Iterative refinement / advanced prompting

structured input componentsoutput format specificationschain-of-thoughtfeedback loops
Key: Structured input → stability and predictable formatting. Chain-of-thought → consistent reasoning quality across complex documents.
Trap: On "Select TWO", pick options covering different needs (one input-structure, one reasoning) rather than two that both address input. Narrative/stylistic polish and terminology glossaries are plausible distractors addressing neither.

1.6.6 Complex prompt systems

Bedrock Prompt Flowsconditional branchingreusable componentspre/post-processing
Key: Prompt Flows = sequential prompt chains, branching on model responses, reusable prompt blocks, integrated pre- and post-processing; also the no-code workflow builder.
Watch: Prompt Flows orchestrate prompts. Agentic tool-calling and ReAct loops belong to Agents or Step Functions (Domain 2), not Prompt Flows.
